# ADR-0002: Um banco por serviço, Flyway e Testcontainers

- **Status:** Aceita
- **Data:** 2026-11-04

## Contexto

Microsserviços que compartilham tabelas ficam acoplados pelo esquema: uma mudança em uma coluna quebra outro
serviço e impede o deploy independente.

## Decisão

1. **Database per service**: cada serviço tem seu próprio banco lógico (`customer_db`, `product_db`,
   `inventory_db`, `order_db`). Localmente, os quatro ficam no mesmo container PostgreSQL para economizar
   recursos. Em produção, poderiam ser instâncias separadas sem mudar uma linha de código.
2. **Nenhuma chave estrangeira entre serviços**: `orders.customer_id` é apenas um número. A integridade é
   garantida pela API: o Order consulta o Customer antes de gravar.
3. **Flyway** versiona o esquema (`src/main/resources/db/migration/V1__*.sql`). O Hibernate apenas **valida**
   o esquema (`ddl-auto: validate`) e nunca o altera.
4. **Testes em dois níveis**:
   - H2 (modo PostgreSQL) para testes rápidos de repositório e de controller (`*Test`), executados a cada build.
   - PostgreSQL real com **Testcontainers** (`*IT`), executados pelo `maven-failsafe-plugin`. Assim, as
     migrations e as consultas são validadas no banco de produção (tipos, locks, constraints).
5. As migrations usam SQL compatível com os dois bancos (`BIGINT GENERATED BY DEFAULT AS IDENTITY`,
   `NUMERIC`, `TIMESTAMP WITH TIME ZONE`).

## Consequências

- (+) Cada serviço evolui seu esquema de forma independente.
- (+) Os testes com Testcontainers pegam diferenças que o H2 esconderia. Exemplo: o teste de concorrência
  do Inventory valida o `SELECT ... FOR UPDATE` no PostgreSQL.
- (-) Consultas que cruzam contextos (ex.: "pedidos com o nome do cliente") exigem composição via API ou
  uma réplica de leitura (CQRS), mais trabalhosas que um JOIN.
- (-) Os testes `*IT` exigem Docker. Sem Docker, use `./mvnw verify -DskipITs`. No CI, eles sempre rodam.
